# 版本与发布

本文档是版本号的唯一权威。`MILESTONES.md` 的出口标准、`CI.md` 的发布流程都以这里为准。

## 1. 版本格式

```
0 . <里程碑号> . <发版序号> - preview . <重建号>
└┬┘ └────┬────┘ └───┬────┘   └──┬──┘   └──┬──┘
 │       │          │           │         └─ 同一次发版的重打：签名失败、构建失败、tag 打错
 │       │          │           └─ 未正式发布前恒定存在
 │       │          └─ 该里程碑内的第 N 次发版，从 1 开始
 │       └─ P0–P6 直接对应，不做 +1 偏移
 └─ 未经明确声明，恒为 0
```

| 位置 | 含义 | 由谁改 | 规则 |
|---|---|---|---|
| 第一部分 | 大版本 | 只有维护者明确声明时才 +1 | 其余时间恒为 `0` |
| 第二部分 | 里程碑 | 里程碑切换时 +1 | 与 `MILESTONES.md` 的 P 编号一一对应：P3 → `0.3` |
| 第三部分 | 发版序号 | 每次打 tag 时 +1 | 同一里程碑内单调递增，不跳号 |
| `-preview.N` | 预览标记 | 每次打 tag 默认带上 | 正式发布前**所有** tag 必带 |

**不做 +1 偏移**：P3 就是 `0.3`，不是 `0.4`。读版号就能直接翻到里程碑文档，不需要心算。

**为什么不把 patch 按"每个功能/修复 +1"**：那样一次里程碑会产出几十个 tag，发布页会变成噪音，而 `-preview.N` 与 patch 的职责也会重叠。所以：

- **每个功能/修复 = 一个 commit**（PR 级 squash，Conventional Commits 标题）；
- **每次发版 = patch +1**，一个 tag 对应一个可安装、可回滚的点。

## 2. 版本线

| 里程碑 | 版本线 | 首个 tag | 说明 |
|---|---|---|---|
| P0 地基 | `0.0.x` | `v0.0.1-preview.1` | 能装、功能为空 |
| P1 编辑器 alpha | `0.1.x` | `v0.1.1-preview.1` | |
| P2 首个 pre-release | `0.2.x` | `v0.2.1-preview.1` | 对外可下载 |
| P3 Agent 可用 | `0.3.x` | `v0.3.1-preview.1` | |
| P4 工作台与并行 | `0.4.x` | `v0.4.1-preview.1` | |
| P5 数据库与周边 | `0.5.x` | `v0.5.1-preview.1` | |
| P6 稳定化与鸿蒙 | `0.6.x` | `v0.6.1-preview.1` | |
| 正式版 | `1.0.0` | `v1.0.0` | 仅维护者明确声明时 |

## 3. 打 tag 的时机

| 时机 | tag | 是否必须 |
|---|---|---|
| 里程碑内，用户可感知的功能落地 | `0.<P>.<N+1>-preview.1` | 建议 |
| 里程碑内，高危安全修复 | `0.<P>.<N+1>-preview.1` | 必须 |
| 里程碑结束，功能完成且已知 bug 清空 | `0.<P>.<N+1>-preview.1` | **必须** |
| 维护者声明正式版 | `v1.0.0` | 手动 |

里程碑收尾的 tag 与中间 tag 格式相同——**没有"里程碑完成版"这种特殊后缀**。里程碑是否完成，看 release notes 与 `MILESTONES.md` 的勾选，不看版本号。

## 4. 正式版

只有维护者明确说明时，才打**不带后缀**的 tag：

```
v1.0.0
```

同时第一部分从 `0` 升到 `1`。这一步不可拆：不存在 `v0.7.0` 这种"正式版"。

`1.0.0` 之后的规则：

- 第二部分**不再绑定里程碑编号**（里程碑是开发期概念），改为按特性批次递增；
- 第三部分仍是发版序号；
- `-preview.N` 后缀依然可在正式版前的预发布中使用；
- 破坏性变更只在第一部分递增时允许。

## 5. 应用内版本号

三处必须与 tag 完全一致（`CI.md` 与 `release.yml` 有断言）：

| 位置 | 示例 |
|---|---|
| `Cargo.toml` workspace `version` | `0.3.1-preview.1` |
| `package.json` `version` | `0.3.1-preview.1` |
| `apps/desktop/src-tauri/tauri.conf.json` `version` | `0.3.1-preview.1` |

前提：`0.3.1-preview.1` 是合法的 semver，三处都接受。**不要**写成 `0.3.1-preview1`（缺少点号会导致排序错误）或 `0.3.1-pre`（`pre < preview`，语义混乱）。

UI 上：窗口标题与"关于"页显示完整版本号；`-preview` 存在时标题栏加一个 `preview` 徽标，状态栏不显示版本号（避免干扰）。

## 6. tag 的机械校验

规则写在文档里没用，必须让 CI 拒绝违规 tag。`release.yml` 的 `prep` 在构建前断言：

```
^0\.[0-9]+\.[0-9]+-preview\.[0-9]+$   → 通过，prerelease = true
^[1-9][0-9]*\.[0-9]+\.[0-9]+$         → 通过，prerelease = false（正式版）
其他                                   → 失败
```

三件事因此变得不可能：`0.x` 漏带 `preview`、`preview` 少写点号、正式版用 `0.x`。

GitHub Release 的 `--prerelease` 由后缀自动决定，不靠人勾选。

## 7. 提交与变更日志

- **一个 PR = 一个 commit**（squash），标题用 Conventional Commits：`feat(agent): …` / `fix(db): …` / `perf(fs): …`。
- scope 用 lane 或 crate 名：`fs` `editor` `agent` `db` `ci` `proto`。
- `CHANGELOG.md` 按 Keep a Changelog 维护，分 `Added / Changed / Fixed / Security`；发版时由 commit 标题生成初稿，人工合并同类项。
- `fix` 与 `security` 类条目必须写影响范围与规避方式，不能只写"修复若干问题"。

## 8. 契约版本独立

`lc-proto` 有自己的版本，与 app 版本解耦：

| 场景 | 契约版本 |
|---|---|
| 新增可选字段、新增命令 | minor +1 |
| 删除/改名/改语义 | major +1，独立 `[contract]` PR |
| 仅生成代码变化 | patch +1 |

app 版本升级不代表契约兼容性变化；反过来契约 major 升级必须在 app 的 release notes 里显式标注。
